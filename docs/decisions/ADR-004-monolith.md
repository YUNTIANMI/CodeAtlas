# ADR-004：采用模块化单体，不采用微服务

- **状态：** 已接受
- **日期：** 2026-09-12

## 背景

系统包含用户、项目、文档、代码、Git、AI 等多个相对独立的业务域。在设计初期需要决定是按微服务拆分，还是保持单体。

## 决策

采用 **模块化单体架构（Modular Monolith）**：

- 单一 Spring Boot 应用部署
- 内部按业务域划分包结构：`user`、`project`、`document`、`code`、`git`、`ai`、`common`
- 模块间通过 Service 接口交互，不直接跨模块访问数据库表

## 理由

1. **开发主体是个人**：微服务的部署、监控、联调成本远超单人可承受范围。
2. **微服务不是工程能力的必要条件**：分层清晰、边界明确、可测试可部署的单体，同样能体现软件工程水平。
3. **迭代速度优先**：单体下改一个字段、调一个接口，本地一键启动即可验证。
4. **AI 模块天然适合内聚**：RAG 链路（检索→拼装→调用→记录）是需要事务与上下文连续性的流程，拆出去会引入分布式调用与重试问题。
5. **避免过度设计**：项目尚未验证核心价值，过早拆分会锁死错误的边界。

## 备选方案

| 方案 | 未采用原因 |
|---|---|
| 按域拆分为独立微服务 | 部署复杂、联调困难、个人维护成本过高 |
| 只把 AI 服务独立出去 | AI 模块强依赖项目数据，拆出去后每次调用都要跨服务鉴权与取数 |

## 影响

- 必须靠**包结构与代码规范**维持模块边界：禁止跨模块直接访问对方 Repository
- 未来若确需拆分，模块化单体可按包边界低成本拆出
- 所有模块共享同一个数据库，需在应用层严格保证数据所有权边界

## 复审条件

出现以下任一情况时重新评估：

- 团队规模超过 3 人并行开发
- 某个模块（如 AI 推理）出现明显不同的资源需求或伸缩需求
- 部署频率差异过大，部分模块需要独立发布
